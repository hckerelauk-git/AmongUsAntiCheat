# 02 · 核心原理

本文解释 Apex Cheat Ender 为什么这样设计，以及支撑判定的几个核心机制。

---

## 1. 判定模型：规则命中，而不是分数累积

### 1.1 为什么不用分数

早期反作弊常见做法是「可疑度累加 + 时间衰减 + 阈值判定」：每条证据给一个分值，
分数超过阈值就处置。这套模型有三个致命问题：

1. **不可解释**。玩家被处置时，你无法回答「到底是哪条规则把他判掉的」，
   因为结论来自一堆分值相加。
2. **需要调参**。阈值、权重、衰减速率互相耦合，换张地图或换个玩法就要重调。
3. **确定性证据被稀释**。一次「非内鬼击杀」是物理上不可能发生的，
   但它可能被一个高分阈值「平均」掉。

### 1.2 现行模型

Apex Cheat Ender 改为**规则命中**：

- 每条规则命中即记一笔（`EvidenceCount++`）；
- 命中 `Critical` 严重度的规则 → 直接定为 `HighRisk`，**不参与任何加权**；
- 没有分数、没有衰减、没有「多少分」这种配置项。

**关键性质**：确定性的东西不该被时间洗掉，也不该被其他证据的多少影响。

### 1.3 去重机制

同一条规则在 **0.25 秒内**对同一玩家只记一次（`VerdictEngine.Submit` 内的时间戳比对）。
这解决的是「同一次动作被多个 Hook / RPC 路径重复触发」的问题——
否则一次击杀就能把命中条数瞬间刷满。

---

## 2. 分层架构

检测被拆成四层，每层的证据置信度与处理方式不同：

```
┌─────────────────────────────────────────────────────────┐
│ L1 静态层  ModScanner + CheatSignatureDb                │
│    「作弊软件是否存在」                                   │
│    置信度最高（存在性判断）→ 全局证据，不归属具体玩家      │
├─────────────────────────────────────────────────────────┤
│ L2 行为层  BehaviorAnalyzer.AnalyzeMovement              │
│    「移动是否物理上可能」                                 │
│    需时间窗口累计 → 采样驱动                              │
├─────────────────────────────────────────────────────────┤
│ L3 事件层  AnalyzeKill / AnalyzeTask / AnalyzeVentUse    │
│    「动作在当前状态下是否合法」                            │
│    动作触发式 → Harmony 补丁驱动                          │
├─────────────────────────────────────────────────────────┤
│ L4 网络层  RpcFloodGuard / SnapToPatch                   │
│    「协议流量是否异常」                                   │
│    前缀拦截式 → 只有房主真正丢弃                          │
└─────────────────────────────────────────────────────────┘
```

四层产出的都是同一种「货币」：`Violation` 对象。
它被统一投递给判定层 `VerdictEngine`，由后者汇总成 `PlayerVerdict`。

---

## 3. 降误报的三道闸门

行为检测最大的敌人是误报。Apex Cheat Ender 用三道独立的闸门叠加压制：

### 闸门一：合法传送豁免窗口

正常对局中存在**合法的位置突变**：回合开始传送、会议前后重排、进出通风管、网络重同步。
Apex Cheat Ender 用一个时间戳 `LastLegalTeleportTime` 标记这些时刻，
在 **0.35 秒**窗口内的位移**一律不判定位移异常**。

触发豁免的时机：

- 会议开始 / 结束时，对**所有**玩家打标；
- 玩家进入通风管时；
- 收到 `RpcSnapTo` 时（网络重同步）。

### 闸门二：抖动容差

小于 `多小的位移算正常抖动`（默认 0.35）的位移直接忽略。
网络同步本身就有噪声，不做容差会产生大量无意义证据。

### 闸门三：连续命中计数

单次异常不成立。超速需要连续 `超速几次才记下来`（默认 3）次采样都超限，
才升级为正式证据。任何一次回到正常范围都会让计数器衰减。

---

## 4. 房主唯一丢弃权

**只有房主才能丢弃 RPC 或踢人**，且判定入口唯一：

```csharp
GameBridge.IsHost   // = AmongUsClient.Instance.AmHost
```

为什么必须这样：

- 非房主丢弃 RPC 会造成**自己视角与其他玩家不一致**，表现为「看到别人瞬移」，
  反而破坏对局；
- 房主是房间权威，它的丢弃会被其他客户端接受。

唯一的例外是 `RpcFloodGuard`：它对**所有玩家**都做速率统计，
但真正 `return false` 丢弃仍然只在 `IsHost` 时执行（见 `RpcFloodPatches.Prefix`）。

---

## 5. 主线程约束

Unity 的 il2cpp 对象**只能在主线程访问**。Apex Cheat Ender 有一处异步逻辑（AI 分析），
它的处理方式是：

1. 主线程 `MaybeAnalyze` → 抓取快照 → `Task.Run` 丢到后台线程发 HTTP；
2. 后台线程把结果写入 `ConcurrentQueue<Violation>`；
3. **主线程**每帧 `DrainPending` 取出并提交给判定层。

> 后台线程**绝不**直接触碰 Unity 对象。`CaptureSnapshot` 在派发前就在主线程完成了。

---

## 6. 补丁鲁棒性设计

Among Us 每个大版本都会改方法签名。Apex Cheat Ender 的应对策略：

| 设计 | 目的 |
|---|---|
| 按**方法名**查找目标，不硬编码签名 | 参数增减后依然能挂上 |
| 用 `object[] __args` 通用取参 | 不依赖具体参数类型与顺序 |
| 优先选**公开重载**，退而求其次选私有 | 公开方法才是游戏的正常调用入口 |
| 逐个挂载，单个失败只警告不中断 | 某个方法改名不会导致整套检测瘫痪 |
| 所有检测逻辑包在 `PatchHelper.Safe` 里 | 检测异常绝不影响游戏运行 |
| `GameBridge` 每处访问都 try/catch + 多路径降级 | 游戏更新后最多失去某项能力，不会崩进程 |

---

## 7. 可解释性

每条 `Violation` 都带两个字段，保证「为什么判他」可回答：

- `Detail`：人类可读的描述，直接进日志；
- `Metrics`：结构化数值（距离、速度、阈值、前后坐标等），便于事后调参。

示例（瞬移证据的 Metrics）：

```
distance, delta_time, threshold, strike_count, from_x, from_y, to_x, to_y
```

被误判的玩家可以凭这些数值申诉，房主可以据此判断是作弊还是网络问题。

---

## 8. 配置热重载

调参天然是一个「改一点 → 进游戏试 → 再改」的过程，要求重启游戏是不可接受的。

Apex Cheat Ender 的做法（`ConfigHotReloader`）：

1. 每 **0.5 秒**检查配置文件的修改时间与长度；
2. 发现变化 → `Reload()` 重新读盘；
3. **Diff 新旧值**，只广播真正变化的项。

为什么不能只靠 `SettingChanged` 事件：该事件只在代码里赋值时触发，
用户在记事本里改文件不会触发。

为什么不无条件 `Reload`：无差别重载会让补丁被反复挂载 / 卸载，
因此必须先 Diff 再动作。
